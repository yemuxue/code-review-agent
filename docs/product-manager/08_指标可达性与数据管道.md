# 指标可达性对照表：从指标树到真实数据管道

> 本文回答 [05_指标体系与实验方案.md](05_指标体系与实验方案.md) 留下的最大缺口：
> **指标树里列出的每一项，今天到底有没有数据能算出来。**
>
> 结论先行：**已落地的是"轨迹 / 效率成本 / 稳定性 / 采集健康度"四类，它们全部来自
> 同一个自产数据源（Agent 的 JSONL 遥测）**；结果质量（Precision/Recall/F1）来自
> 两份人工标注集，目前只能在**手动触发的真实 API 评测**中产出；
> 用户价值类指标（有帮助率、采纳率、节省时长）**当前完全无数据源**，
> 因为对应的产品埋点还没有实现。任何引用这些数字的材料都必须标注其口径与局限。

### 最新真实读数（2026-10-13，全量 124 条）

> **📌 权威口径与引用规则见 [评测基线：严格标准下的精确优先](../eval-baseline.md)。**
> 该页给出运行配置、漏报构成、引用时可以说/不可以说的话，以及后续改动的衡量方法。

| 项 | 值 |
|---|---|
| 模型 | `gpt-6-sol`，温度 0.0，`reasoning_effort=high`（responses 协议） |
| 数据集 | `llm-agent-qa-system-labeled` **v1.2.0** |
| 判分完整性 | **124/124 已判分，零跳过零异常** |
| Precision / Recall / F1 | **94.0% / 56.0% / 0.70** |
| 混淆矩阵 | TP=47、FP=3、FN=37、TN=37 |

**这个基线是"精确优先"的定位**：模型只报有把握的缺陷，因此精确率高、
召回率中等。37 条漏报里 **30 条是"模型认为不该报、而标注标准认为该报"的
口径分歧**，只有 7 条属"模型该报而没报"。

两条提高召回率的提示词路径（放宽判据、改开放式枚举）**均经实验证伪**，
故接受该召回率而非用放宽标准换数字。要改变这个数只能做产品口径决策。

#### 三个版本的口径漂移（同一次模型运行）

| 指标 | v1.0.0 原始 | v1.1.0 翻转失效标注 | **v1.2.0 收回仍含缺陷的** |
|---|---|---|---|
| Precision | 94.0% | 94.0% | **94.0%** |
| Recall | 43.5% | 58.0% | **56.0%** |
| F1 | 0.59 | 0.72 | **0.70** |
| 正例分母 | 108 | 81 | **84** |

**跨版本读数不可直接比较**，引用必须给出 dataset version。

注意 v1.1.0 → v1.2.0 的召回率是**下降**的：复核发现 3 条"已修复"负例
其实仍含其它真实缺陷，改回正例后分母变大。**修标注既可能升也可能降读数** ——
这正是它可信的原因。

### 标签修正是怎么做的（2026-10-13）

2026-10-07 的漏报归因显示，61 个漏报中 **29 条（48%）的标注描述在当前代码里
已不存在**。逐条读源码复核后处置为：

| 处置 | 条数 | 含义 |
|---|---|---|
| **RELOCATE** | 2 | 缺陷确实仍在，只是行号漂移（`prompt.py` 75→76、85→106） |
| **RELABEL_NEGATIVE** | 27 | 该位置代码现在正确 → 翻成负例（FP 陷阱），描述加【已修复】前缀 |

处置原则：**不删除任何样本**，总数仍为 124 条 —— 标签修正不等于缩小测试集，
否则"召回率提升"会来自分母变小而非能力提升。被翻转的 27 条同时成为新的
FP 陷阱：模型在那里报出即为误报。

**专业性说明**：这次修正没有、也不应该去修改被评测项目 `llm-agent-qa-system`
的源码 —— 那是把可评测样本变成失效样本，等于自己降低评测难度。

**没有改变的部分**：27 条"判据口径分歧"的标注**保持原样**。
它们描述的缺陷在当前代码里客观存在（死代码、恒用分支、重复实现等），
只是优先级低。是否算"问题"取决于产品口径，不能单方面改标签。

#### 漏报归因依据（2026-10-07，v1.0.0 标签下）

对 61 个漏报逐条读源码归因后，结论与直觉相反：

| 归因 | 条数 | 占比 | 处置（2026-10-13） |
|---|---|---|---|
| 标注失效（描述的缺陷在当前代码里不存在 / 已修复 / 与代码矛盾） | 29 | 48% | 2 条重定位、27 条翻为负例 |
| 判据口径分歧（维护性 / 风格类，模型答 NO 合理） | 27 | 44% | **保持原样**（缺陷客观存在，仅优先级低） |
| 上下文不足（证据在 ±15 行窗口之外） | 2 | 3% | 保持原样 |
| **真实漏报（模型确实判断错误）** | **2** | **3%** | 保持原样（是被评测项目的代码缺陷） |
| 无法判定（需运行时数据） | 1 | 2% | 保持原样 |

**严重度交叉**：**High 严重度漏报 0 条**（全数据集 4 个 High 全部命中），
漏报全部集中在 Low（47/61）与 Medium（14/61）。

代表性反例：`react_agent.py:222` 标注称"无异常处理"，而源码 221–225 行就是
`try/except`；`react_agent.py:97` 标注称"默认参数导致实例共享"，而代码在
`__init__` 体内每实例新建。

**由此得到的关键决策**：修标注之前**不要**为提高 Recall 放宽判定提示词 ——
那只会让模型对"已被修复的旧问题"报 YES，推高误报而无真实收益。

**评测方法论缺口（已部分补齐）**：`preflight()` 只校验
「文件存在 + 行号在范围内」，**不校验「该行是否仍有标注所描述的问题」**。
这比"三份矛盾读数"更根本。

2026-10-13 的补齐：
- **锚点指纹**（`tests/eval/anchors.py`）机制上检测「该行内容是否已变」，
  可防**未来**失效（OK / RELOCATED / CHANGED / MISSING）；
- 但锚点**不能检测已有的语义失效** —— 只能记录"构建锚点那一刻"的内容。
  已有的 29 条是靠一次性逐条读源码归因发现的，无法自动化。

**本轮补齐的两件事**

1. **标注集可机器校验**：每个数据集有 `dataset_id` 与 `version`，`preflight()`
   逐条校验文件存在、行号在范围内、枚举合法、`DATASET_META` 计数与实际一致，
   并拒绝歧义 basename（外部项目里 `agent/tools/base.py`、`llm/base.py`、
   `memory/base.py` 三个同名文件，旧实现按文件名兜底会指到错误位置）。
   CI 有独立作业，改坏标注直接失败。
2. **跳过与异常显式记账**：`score_samples()` 返回 `healthy` 判据
   （全部样本被计分且无判分异常）。`healthy=False` 时 precision/recall
   只是部分样本的读数，`--gate` 下直接失败——旧实现文件找不到就 `continue`，
   只让 `scanned < total` 偷偷暴露（历史事故：16/124 未被发现）。

**已知口径问题（必须随数字一起说明）**：
- 真实评测里 API 调用失败的样本被计为 FN，因此"运行口径"的 Recall 会低于
  "模型响应口径"。两个口径都必须保留，不能只报好看的那个。
- 同一份 124 条标注集历史上出现过三份互不一致的读数（TP=48 / TP=41 等），
  原因是模型版本、提示词版本与运行口径都不同。本轮起 replay 产物会写入
  `dataset_version` / `model` / `temperature` / `target_dir` / `skipped` /
  `errored` / `healthy` / `run_at`，使后续读数可调和；**历史产物无法追溯**。
- 离线判分（注入桩）验证的是"计分与数据管道正确"，**不是模型质量**。

## 3. 轨迹层（✅ 全部落地）

| 指标 | 数据源事件 | 计算函数 | 目标值 |
|---|---|---|---|
| 工具调用成功率 | `tool_call_end.error` | `metrics.tool_success_rate` | ≥98% |
| 参数合法率 | `tool_call_start.args_ok` | `metrics.args_valid_rate` | ≥95% |
| Plan 可执行率 | `parse_result(role=planner,kind=findings)` | `metrics.plan_parse_rate` | ≥95% |
| VERDICT 解析率 | `parse_result(role=executor,kind=verdict)` | `metrics.verdict_parse_rate` | ≥95% |
| fix 输出解析率 | `parse_result(role=fixer,kind=fix)` | `metrics.fix_parse_rate` | ≥95% |
| 空转率 | `turn_start`/`turn_end` 序列 | `metrics.idle_turn_rate` | ≤10% |
| 循环率 | `tool_call_start.args_fingerprint` 重复计数 | `metrics.loop_rate` | ≤0% |
| 端到端成功率 | `session_end.complete` | `metrics.e2e_success_rate` | ≥90% |
| **降级率** | `session_end.degraded` / `degraded_reason` | `metrics.degradation_rate` | ≤0% |
| turn 预算耗尽率 | `node_stats.max_turns` vs `turns` | `metrics.turn_budget_exhausted_rate` | 建立基线 |

> **降级率为什么必须单独存在**：模型故障、turn 预算耗尽、空最终回答这三类结果
> 都会返回 `HTTP 200` + 一段可读文本，但内容不可信。只看"端到端成功率"会把
> 它们算成成功，从而**系统性高估质量**。降级状态由 `AgentHarness.degraded`
> 与 `LangGraphOrchestrator._run_degradation` 显式标记后写入遥测，
> API 响应体也带 `degraded` + `error_code`，让调用方不必解析文本就能判断。

> 目标值集中在 `src/eval/report.py::TARGETS`，由 `src/eval/baseline.py::evaluate_targets`
> 直接消费。**阈值只有一份来源**，报告展示与 CI 门禁共用，不存在两处漂移。

## 8. 用户价值层（🔴 全部无数据源）

| 指标 | 规划的事件 | 实现状态 |
|---|---|---|
| 有帮助率 | `finding_feedback` | 事件不存在 |
| 采纳率 | `patch_approved` / finding 状态流转 | 事件不存在 |
| 节省审查时长 | `review_started` / `review_completed` 时间差 | 事件不存在 |

| 单位活跃团队成本 | 成本 / 活跃团队 | 依赖上述 + 租户模型 |

**这是当前最关键的产品缺口**：没有这一层，"发现得准不准"能回答，
但"用户是否因此受益、值多少钱"无法回答——而后者才是商业化决策依据。
补齐它需要的是产品埋点 + 真实试点用户，不是更多代码。

### 8.1 服务端已有、但还不能当产品指标用的信号

本轮补齐了**服务端审计闭环**（谁在什么时候对哪个项目做了什么）：
请求 ID 贯穿日志/遥测/数据库，`logs` 表有 actor/request_id/file_path/outcome，
登录成败、分析开始/完成/降级、越权访问全部落审计。

但请注意口径差异：这些是**系统侧审计**，回答"系统为谁做了什么"，
**不等于用户价值**。它们可作为用户价值指标的前置埋点基础
（例如"分析完成"可以作为"节省时长"的分母），但缺少用户侧反馈信号，
仍然算不出采纳率与有帮助率。

| 已可查（服务端审计） | 仍缺（需产品埋点） |
|---|---|
| 谁发起了分析、目标项目是哪个、何时 | 用户是否采纳了某条发现 |
| 分析是否降级/失败、失败原因码 | 用户是否标记"有帮助" |
| 越权访问尝试 | 首条结果呈现时刻（用户侧时延） |

## 9. 发布决策用法

CI 上的门禁（`.github/workflows/ci.yml::eval-gate`）依次判定三件事，
任何一件失败即阻断合并：

1. **故障注入断言**：10 条离线用例 × repeat 全部通过（行为回归）；
2. **指标目标值**：`TARGETS` 中每项达标；`REQUIRED_METRICS` 无样本即失败（fail-closed）；
3. **基线回归**：与入库的 `reports/eval_offline_baseline.json` 比对，
   指标变差、失败计数增加、采集覆盖度下降都会被判为回归。

| 05 文档的指标树分支 | 本文对应章节 | 可用性 |
|---|---|---|
| 结果质量 | §2 | 🟡 手动评测可得 |

**一句话结论**：工程侧的四层指标已经"可算、可门禁、可回归比对"；
产品侧的用户价值指标仍是空白。任何对外材料引用质量数字时，
必须同时给出数据源（标注集版本）、运行口径（是否含 API 失败）与样本量。
