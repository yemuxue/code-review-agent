# 评测基线：严格标准下的精确优先

> **这是本项目当前唯一权威的代码审查质量基线。** 任何引用审查能力的表述
> 都必须以本页数字为准，并注明数据集版本。
>
> 记录文件（机器可读）：[`tests/eval/replay_baseline.json`](../tests/eval/replay_baseline.json)

## 1. 基线读数

| 项 | 值 |
|---|---|
| **Precision** | **94.0%**（47 / 50） |
| **Recall** | **56.0%**（47 / 84） |
| **F1** | **0.70** |
| 混淆矩阵 | TP=47、FP=3、FN=37、TN=37 |
| 样本总数 | 124（正例 84、负例 40） |

### 运行配置（引用时必须一并给出）

| 项 | 值 |
|---|---|
| 数据集 | `llm-agent-qa-system-labeled` **v1.2.0** |
| 被测项目 | `llm-agent-qa-system`（第三方项目，独立副本） |
| 模型 | `gpt-6-sol`，温度 0.0 |
| 协议 / 思考度 | `responses` / `reasoning_effort=high` |
| 判分 | `per_sample_llm_judgement`（真实模型逐样本判定） |
| 判据变体 | `strict`，上下文窗口 ±15 行 |
| 判分完整性 | 124/124 已判分，零跳过、零异常（`healthy=true`） |

## 2. 这个基线的定位：精确优先

**模型的策略是"只报有把握的缺陷"。** 它不会为了凑数量而报出低置信度的问题，
因此精确率很高（94.0%），而召回率中等（56.0%）。

具体表现：模型对维护性一类问题（死代码、重复实现、恒不可用分支、微优化）
倾向于判为"不值得报"。这类问题在标注集里是**正例**，所以计入漏报。

### 漏报 37 条的构成（这个数字必须连构成一起看）

| 构成 | 条数 | 性质 |
|---|---|---|
| 判据口径分歧（客观低优先级维护性问题） | 30 | **产品口径问题**，非模型能力 |
| 本次复核收回的真实缺陷 | 3 | 模型确实漏掉（已修标注并计入） |
| 重定位标注后仍漏 | 2 | 缺陷真实存在，模型未报 |
| 真实漏报（模型判断错误） | 2 | 模型能力 |
| 合计 | 37 | |

**即：37 条漏报里只有 7 条（3+2+2）属于"模型该报而没报"。**
其余 30 条是"模型认为不该报，而标注标准认为该报"。

## 3. 为什么接受这个召回率

**建议提高召回率的两条路径都被实验证伪**，因此这不是"没试过就接受"：

### 实验 #1：放宽判定判据（+ 放大上下文窗口）

| 指标 | strict @±15 | lenient @±40 |
|---|---|---|
| Precision | 93.8% | 100.0% |
| **Recall** | **38.5%** | **23.1%** |

逐样本翻转：**FN→TP 仅 2 条且全部来自已失效标注（假改善）**，
**TP→FN 有 8 条**（基线本来正确）。**可信改善 = 0。**

模型给出的"NO"理由与独立人工归因逐条吻合——它说"这段代码是对的"，
而读源码确认它是对的。→ [`recall_experiment_01.md`](../reports/recall_experiment_01.md)

### 实验 #2：改提问形状（开放式枚举替代二值提问）

| 分组 | 已完成 | 结果 |
|---|---|---|
| 口径分歧（待召回） | 3/30 | **全部仍是 FN** |
| TP 对照（查回归） | 2/10 | 无回归 |

枚举提问同样无法召回这些样本。→ [`recall_experiment_02.md`](../reports/recall_experiment_02.md)

### 结论

> **要改变这个数字，只能做产品口径决策，而不是继续调提示词。**

## 4. 引用规则（避免误读）

**可以说：**

- "在 124 条人工标注、v1.2.0 的评测集上，`gpt-6-sol`（high 思考度）精确率
  94.0%、召回率 56.0%、F1 0.70，124/124 全部判分成功。"
- "该配置采取精确优先策略：只报有把握的缺陷，漏报集中在低优先级维护性问题。"

**不可以说：**

- ❌ "召回率 56.0%" 而**不注明数据集版本** —— v1.0.0 的分母是 108，
  v1.1.0 是 81，v1.2.0 是 84，跨版本相减没有意义。
- ❌ 把 56.0% 描述成"模型只能发现一半问题"——37 条漏报中 30 条是口径分歧。
- ❌ 与其它工具的数字直接比较，除非数据集、版本、判据、模型完全一致。
- ❌ 用离线桩判分（`stub-yes`/`stub-no`）的读数代表模型质量。那类运行只验证
  评测管道本身，其 P/R/F1 是**同义反复**的。

## 5. 如何衡量后续改动

```bash
# 1) 跑一次真实评测（需要外部项目副本与可用的 API 网关）
python -m tests.eval.runner --suite replay --allow-live --dataset external \
  --target-dir <llm-agent-qa-system 路径> --samples 124 \
  --sample-delay 1 --sample-retries 1 --circuit-breaker 15 \
  --report reports/eval_replay_new.md

# 2) 与基线比对（配置/版本不一致会拒绝比较并以非零码退出）
python scripts/replay_baseline.py check reports/eval_replay_new_*.json
```

门禁的判定：

| 退出码 | 含义 |
|---|---|
| 0 | 无显著变化（容差 ±2pp），或有改善 |
| 1 | **回归**（精确率/召回率/F1 超出容差下降） |
| 3 | **不可比较** —— 数据集版本 / 模型 / 判据 / 窗口 / 判分方式不一致 |

**退出码 3 是保护而非故障**：它拦住"拿不可比的读数相减"这类错误，
历史上正是这种比较产出了三份互相矛盾且无法调和的读数。

### 改标签时必须升版本

若修改标注（新增、修正、翻转），必须：

1. 递增 `DATASET_META["version"]` 并同步 `real_bug_count` / `fp_trap_count`；
2. 重建锚点指纹（`python -m tests.eval.anchors build --dataset ... --target-dir ...`）；
3. 用 `scripts/recompute_metrics.py` **零 API 成本**重算既有产物；
4. 用 `scripts/replay_baseline.py record` 更新基线记录。

## 6. 已知局限（当前读数的不确定来源）

| 局限 | 影响 |
|---|---|
| `tools/calculator.py:105` 有两条标注共用同一位置 | 该位置一次检出会计入 2 次 TP（已在 preflight 告警） |
| 判分是**按位置**匹配，非按缺陷内容匹配 | 模型在该位置报出**另一个**真实缺陷也算 TP |
| 24 条【已修复】负例只排除了原标注所指的问题 | 已因该风险收回 3 条（v1.2.0）；其余经复核确认无其它缺陷 |
| 标注由人工编写，判据含主观成分 | 30 条口径分歧正是这一点的体现 |
| 网关延迟波动大（单样本 20s ~ 2min） | 全量 124 条需 1~3 小时；失败样本用 `scripts/replay_retry_samples.py` 单独补跑 |
| 基线那次运行早于 `judge_variant` 字段落盘 | `strict` / ±15 为**推断**，已在记录里显式标注 |

## 7. 何时应当重新审视这个基线

- 模型换代（例如换到更强的推理模型）后重跑；
- 数据集扩充或标注标准修订后；
- 若产品决定把维护性问题作为独立类别要求报出 —— 那需要先改判据标准、
  重跑并记录新基线，而不是修改既有标签去迁就数字。

## 8. 版本沿革

| 数据集版本 | 召回分母 | Recall | 发生了什么 |
|---|---|---|---|
| v1.0.0 | 108 | 43.5% | 原始标注（29 条描述的缺陷已不存在） |
| v1.1.0 | 81 | 58.0% | 翻转 27 条失效标注为负例 |
| **v1.2.0** | **84** | **56.0%** | 复核发现 3 条负例仍含其它真实缺陷，改回正例 |

注意 v1.1.0 → v1.2.0 召回率是**下降**的：修正标签既可能升也可能降读数，
这正是它可信的原因。若一次"修正"只让数字变好，那值得怀疑。
