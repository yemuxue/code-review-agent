# 召回率提升实验报告 #1：放宽判据假设被证伪

> 日期：2026-10-13 ｜ 模型：`gpt-6-sol`（responses 协议，`reasoning_effort=high`）
> 数据集：`llm-agent-qa-system-labeled` v1.0.0（前 40 条，占 124 条的 32%）

## 0. 一句话结论

**"放宽判定判据 + 放大上下文窗口"不仅没有提升召回率，还丢掉了 8 个原本正确的检出，
且零真实收益。** 模型给出的"NO"理由与独立人工归因**逐条吻合**——它在这些位置
是对的，失效的是标注。

## 1. 为什么必须先建立计量基础

原始读数 Recall = 43.5%（全量 124 条）**不能直接当作模型能力**。
漏报归因显示 61 个漏报中：

| 归因 | 条数 | 占比 |
|---|---|---|
| 标注失效（缺陷已不存在/与代码矛盾） | 29 | 48% |
| 判据口径分歧（客观但低优先级） | 27 | 44% |
| 上下文不足 | 2 | 3% |
| **真实漏报** | **2** | **3%** |

因此本轮先加了**标注有效性叠加层**（`tests/eval/validity.py`），
把 STALE 标注排除出召回分母：

| 口径 | 召回率 | 分母 |
|---|---|---|
| 原始 | 43.5% | 108 |
| **有效** | **59.5%** | 79 |

## 2. 实验设计（受控）

只有把"提示词"与"上下文窗口"分开，才能知道提升来自哪一项。

| 臂 | 判据 | 窗口 | 说明 |
|---|---|---|---|
| 基线 | strict | ±15 | 历史口径；**从全量 124 条产物提取前 40 条，零 API 成本** |
| 候选 | lenient | ±40 | 放宽判据（把客观可验证的低优先级缺陷纳入 YES）+ 放大窗口 |

## 3. 结果

| 指标 | strict @±15 | lenient @±40 | 变化 |
|---|---|---|---|
| Precision | 93.8% | 100.0% | +6.2% |
| **Recall** | **38.5%** | **23.1%** | **−15.4%** |
| F1 | 0.55 | 0.38 | −0.17 |
| TP | 15 | 9 | **−6** |
| FP | 1 | 0 | −1 |
| FN | 24 | 30 | +6 |

### 逐样本翻转（39 条共有样本）

| 翻转 | 条数 | 标注有效性 |
|---|---|---|
| FN → TP（改善） | 2 | **全部 STALE** —— 模型开始对已修复的旧问题报 YES |
| TP → FN（回归） | 8 | 基线已检出（推定有效） |
| FP → TN | 1 | — |
| TN → FP | 0 | — |

**可信的召回改善：0 条。**

没有任何有效性叠加层的话，那 2 条 STALE 上的"改善"会被误当成提升。

## 4. 为什么会变差：模型理由与独立归因吻合

对"两轮都判 NO"的 22 条持久性漏报做理由归因：

| 模型理由主题 | 条数 | 占比 |
|---|---|---|
| 认为代码正确/无问题 | 13 | 59% |
| 标注行本身非代码（docstring/注释） | 3 | 14% |
| 认为是有意设计 | 0 | 0% |
| 认为无关紧要/风格 | 0 | 0% |
| 证据不足/看不到 | 0 | 0% |

注意后三项**都是 0**：模型没有把问题当成"style nitpick"敷衍掉，
也没有抱怨证据不足。它明确地说"这段代码是对的"。

这与独立归因**逐条吻合**：

| 样本 | 模型理由（lenient 运行） | 独立归因（读源码） |
|---|---|---|
| `react_agent.py:97` | "the line correctly preserves a supplied memory instance" | 在 `__init__` 体内每实例新建，不存在共享 |
| `react_agent.py:222` | "appending a final user-facing instruction before reques[ting]" | 221–225 已用 try/except 包裹，"无异常处理"不存在 |
| `prompt.py:52` | "`<thinking>` is valid literal text inside the f-string" | XML 是提示词明确约定的协议 |

**两个独立来源得出同一结论** → 这些位置不是模型推理错误，是标注失效。

## 5. 结论与下一步

### 被证伪的假设

> ~~"strict 判据把客观缺陷当成 style nitpick 挡掉了，放宽判据就能提召回"~~

证据：27 条口径分歧里，模型在 lenient 下**仍然**判 NO，理由是"代码正确"；
同时它丢掉了 8 个基线正确的检出。**判据措辞不是杠杆。**

### 真正的阻塞

**28% 的标注（29/108）描述的是当前代码里已不存在的缺陷。**
在这部分被清理之前，任何判据调整都只能在这 79 条有效标注上见效，
而"看起来的提升"很容易来自 STALE 标注上的假改善。

### 下一步（按证据排序）

1. **先修标注**：对 29 条 STALE 逐条决定——重新定位到真实缺陷位置，或标记为
   不计入分母（`validity.py` 已支持后者）。锚点指纹（`tests/eval/anchors.py`）
   已就位，可防止**未来**再次失效。
2. **修完后重跑基线**，得到可信的 Recall，再谈目标。
3. **换杠杆**：若届时 Recall 仍偏低，下一步应改**提问框架**而非判据措辞——
   例如把二值判定改成开放式枚举（"这一行附近有哪些问题？"），
   或先让模型描述代码行为再判定。
   ⚠️ 直接把标注的 category 作为提示输入给判分模型属于**标签泄漏**，
   会虚高指标，不建议。

### 本轮留下的可复用能力

| 工具 | 作用 |
|---|---|
| `tests/eval/validity.py` | 有效性叠加，算出调整后召回率与分母 |
| `tests/eval/judge.py` | `strict`/`lenient` 判据变体 + 可配窗口（受控实验的前提） |
| `scripts/judge_ab.py` | A/B 运行器，**强制同时报告误报变化** |
| `scripts/judge_compare.py` | 净变化 + **逐样本翻转** + 按有效性分层 |
| `scripts/fn_reasons.py` | 用模型理由做归因（离线、零 API 成本） |
| `scripts/ab_from_log.py` | 从日志恢复逐样本判定（含 UTF-16 兼容） |
| `tests/eval/anchors.py` | 锚点指纹，防止标注**未来**失效 |

## 6. 诚实记录

- 本次只跑了 **40/124** 条，未做全量 A/B（约 2.5 小时 + 重复 token）。
  但结论方向由三条独立证据支撑：探测实验、`lenient@15` 早期运行、本次 `lenient@40` 运行，
  三者一致指向"模型在这些位置判 NO 且理由成立"。
- **没有修改被评测项目** `llm-agent-qa-system`：那 2 条真实漏报是它的代码缺陷，
  修改它会把可评测样本变成失效样本。
- 一次运行中出现日志覆盖（两个后台作业写同一文件），候选产物缺失样本 #1 的明细。
  已修复为不同臂写不同文件，不影响结论（39/40 条足够）。
