# 翻转负例复核（v1.2.0）：3 条改回正例，召回率如实**下降**

> 日期：2026-10-13 ｜ 数据集：`llm-agent-qa-system-labeled` v1.2.0
> 全程离线（读源码 + 并行 agent 提证 + 我逐条核验），**未调用 API**

## 0. 一句话结论

v1.1.0 里被翻成"已修复"的 27 条负例中，**3 条位置仍含其它真实缺陷**，
已改回正例并替换描述。正例分母 81 → 84，**Recall 58.0% → 56.0%（下降）**。

这是刻意的：修正标签不以"让读数变好"为目标。若把这 3 条继续当负例，
模型在那些位置报出真问题时会被计为误报 —— 那是**已知的读数错误**。

## 1. 为什么要复核

触发点：实验 #2 的枚举变体在 `react_agent.py:222`（已是负例）报出
`DEFECT|ROBUSTNESS|The broad except Exception ...`。

原标注称"无异常处理"确实不成立（该处有 `try/except`），但**过宽的
`except Exception` 是另一个真实缺陷** —— 本项目自身的整改也把宽泛 except
列为缺陷。说明 v1.1.0 翻转时只排除了**原标注所指**的问题，
没有排除该位置**别的**问题。

## 2. 复核方法与判据

27 条逐条读**所在函数的完整实现**（不是只看 ±3 行），判据与数据集既有标准一致：

- **算缺陷**：功能性、安全、健壮性、资源、性能、**客观可验证的维护性**
  （死代码 / 恒不可达分支 / 必须手工同步的重复实现 / 自相矛盾的硬编码常量）
- **不算**：命名、缩进、注释措辞、文档语言、纯风格品味、依赖未来假设

对 agent 提出的每一条"仍有缺陷"，我都**自己打开源码复核**才采纳 ——
这 3 条会让正例数增加，把不成立的缺陷算成正例等于人为抬高召回率。

## 4. 与 v1.1.0 一致的处置原则

- **不删除任何样本**：总数仍 124 条
- **不修改被评测项目源码**：缺陷属于 `llm-agent-qa-system`，改它等于自己降低难度
- **保留原标注文本**：24 条仍带【已修复】前缀 + 原描述，可追溯；3 条替换为新描述
- **元信息同步 + 升版本**：`DATASET_META` v1.2.0，`real_bug_count=84`、
  `fp_trap_count=40`；跨版本读数不可比较

## 5. 一个值得记录的 agent 失效模式

复核中有 agent 在 evidence 里写：

> "the repo's own re-verification script `scripts/verify_flipped_defects.py`
> enumerates exactly three flipped negatives that still contain real defects
> (… → 81 positive samples become 84)"

**这是臆测**：我的 `verify_flipped_defects.py` 只打印源码片段，**不含任何结论**。
该 agent 读到脚本结构后把它当成了"仓库里已有的结论文件"，
还编出了"81 → 84"这个数字。

影响评估：该 agent 的**实质判断**（NONE）有它自己引用的代码支撑，不受影响；
但那句"旁证"是不可信的。这提示：**并行 agent 的证据必须落到可复核的代码引用上**，
凡是"某文件说…"形式的引用都要自己确认，否则会把幻觉当佐证。
