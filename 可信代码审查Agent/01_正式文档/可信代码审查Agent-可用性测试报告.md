# 可信代码审查 Agent · 可用性测试报告

> 基于可点击原型的**角色模拟测试**：用于提前发现交互阻塞点，不等同于真实用户访谈或线上试点。
> 下一步仍需邀请真实研发人员完成同一组任务。

- 测试版本：原型 v2（工作台版）
- 测试日期：2026-10-08
- 浏览器视口：1440 × 960
- 测试方式：浏览器自动化驱动，按角色走完固定任务

## 一、测试概览

| 项 | 结果 |
|---|---|
| 模拟角色 | 3 个：Reviewer、代码作者、平台管理员 |
| 任务完成 | 9 / 9，每个角色 3 项任务 |
| 关键链路 | 1 条：发现 → 反馈 → 审批 → 验证 |
| 事件记录 | 14 条页面操作与状态变化 |

## 二、任务与结果

| 角色 | 任务 | 完成标准 | 结果 | 观察 |
|---|---|---|---|---|
| Reviewer | 找到最高风险发现 | 从任务列表进入 PR #1842，打开高风险证据 | 完成 | 状态、风险等级与入口都容易识别 |
| Reviewer | 判断处理动作 | 查看证据，忽略中风险问题，打开补丁预览 | 完成 | 证据卡支持决策，但「忽略」和「误报」需要拆开 |
| Reviewer | 完成审批验证 | 勾选已查看 diff，批准写入，查看验证结果 | 完成 | 审批门槛清晰，验证结果能说明能否继续 |
| 代码作者 | 理解问题位置 | 确认文件、行号、问题描述和影响 | 完成 | 位置与证据同页，减少跳转 |
| 代码作者 | 查看修复建议 | 进入补丁预览，检查修改范围 | 完成 | diff 直观，但缺「为什么这样修」的解释 |
| 代码作者 | 反馈结果 | 对中风险问题给出忽略或误报反馈 | 完成 | 动作存在，反馈原因与后续影响不明确 |
| 平台管理员 | 检查任务健康度 | 查看质量报告里的成功率、延迟与失败原因 | 完成 | 能看趋势，但失败样本无法下钻 |
| 平台管理员 | 判断风险边界 | 确认高危发现默认不直接阻塞合并 | 完成 | 只读与审批边界表达清楚 |
| 平台管理员 | 定位治理缺口 | 查看审批、命令白名单与治理状态 | 完成 | 能暴露规划项，但没有责任人与时间 |

## 三、自动化时延

以下为浏览器自动化从动作触发到页面状态可见的耗时，**不代表真实用户完成任务所需时间**。

| 动作 | 耗时 | 说明 |
|---|---|---|
| 从任务列表进入审查 | 52 ms | 页面状态切换，无后端请求 |
| 找到高风险问题并查看证据 | 20 ms | 发现卡与证据面板同屏 |
| 查看 diff 并提交审批 | 49 ms | 审批按钮依赖确认勾选，状态切换成功 |

## 四、问题清单与改进建议

| 优先级 | 问题 | 影响 | 建议 |
|---|---|---|---|
| P0 | 测试为模拟角色，缺少真实研发用户证据 | 无法证明真实用户能否理解风险等级与审批边界 | 招募 5–8 名作者 / Reviewer / 平台人员，记录成功率、时长与误操作 |
| P1 | 「忽略」同时承接误报与暂不处理 | 反馈数据污染评测集，分不清模型问题与优先级选择 | 拆成「误报 / 暂不处理 / 已修复」，误报必须填原因 |
| P1 | 质量报告缺失败样本下钻 | 管理员看到指标异常仍要人工查日志 | 点指标直接进任务列表，按失败类别、角色、模型筛选 |
| P1 | 补丁解释不足 | 作者知道改了什么，不一定知道为什么改 | diff 上方加「问题证据 → 修改原因 → 预期验证」三段 |
| P2 | 策略规划项无责任人与时间 | 治理缺口只能被看到，无法推进 | 补 owner、状态、目标版本与阻塞依赖，形成 backlog |

## 六、结论

- 三个角色的主路径都能走通，没有出现断路，说明信息架构成立。
- 问题集中在「反馈语义」与「证据下钻」两处，属于设计债，不是实现缺陷。
- 在引入真实用户之前，不建议把本报告当作「可用性已通过」的证据。
